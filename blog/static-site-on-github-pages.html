用纯静态 HTML 在 GitHub Pages 上搭个人站

2026 年 10 月 18 日 · 约 5 分钟读完

这个网站没有框架、没有构建步骤，也没有一行 JavaScript。所有的页面都是手写的 HTML，样式集中在一个 CSS 文件里。这并不是因为排斥工具，而是因为内容量小的时候，构建链路的维护成本高于它带来的收益。

为什么不用框架

  • 只有几个页面，不需要路由、组件和状态管理
  • 没有依赖，就没有依赖升级、构建失败和安全公告
  • 首屏只有一个 HTML 和一个 CSS 请求，没有等待编译产物水合的过程

代价是每加一篇文章都要手写一个 HTML 文件。在文章数量少于 20 篇时，这个代价可以接受；超过之后就该换 Astro 或 Hugo 了。

目录结构

让 URL 好看的办法很简单：每个路径一个目录，里面放 index.html。

.
├── index.html          首页
├── projects/
│   ├── index.html      项目列表
│   └── personal-site.html
├── blog/
│   ├── index.html      文章列表
│   └── static-site-on-github-pages.html
├── about/
│   └── index.html
├── resume/
│   └── index.html
├── 404.html
├── feed.xml
├── sitemap.xml
└── style.css

发布

仓库命名成 用户名.github.io，然后在仓库的 Settings → Pages 里选择 main 分支的根目录即可。之后每次 git push 都会自动重新发布，通常一分钟内生效。

三个坑

1. 子路径与绝对路径

用户站点发布在域名根目录，用 /style.css 没问题。但如果以后放到项目站点（/仓库名/）下，绝对路径就会指向错误的位置，要么改成相对路径，要么配置 base。

2. Jekyll 会处理你的文件

GitHub Pages 默认用 Jekyll 构建，以下划线开头的文件和目录会被忽略。在根目录放一个空的 .nojekyll 就能关掉它，避免出现"文件明明推上去了却 404"。

3. 缓存

发布后页面可能还有几分钟的缓存。调试时加上查询参数（如 ?v=2）可以绕过，但不要在生产环境长期这么做。

什么时候该换框架

出现下面任意一条，就值得迁移到静态站点生成器：文章超过 20 篇、需要标签和分页、需要多人协作写稿。迁移成本并不高，因为内容和样式都能直接搬过去。
